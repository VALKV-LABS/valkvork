# Platform Workloads Plan

**This is the current plan, ahead of everything in [NEXT_STEPS.md](../NEXT_STEPS.md) and
[phase-2.md](phase-2.md).** It builds what Valkvork needs to run the Valkv platform's own
services. Each stage adds the features for one service, then that service runs on the
AWS dev cell from the goldenimage repo and is verified.

The services' manifests and the full list of gaps are in valkv-platform-infra,
`environments/dev-workload-example/` (README.md there). This plan covers the first two:

| Stage | Service | Manifest |
|---|---|---|
| 0 | none: the test bed | |
| 1 | Postgres | `global-pg.toml` |
| 2 | The gateway control plane (apg-admin) | `valkv-apg.toml` |

Later stages are listed [at the end](#after-stage-2) but not planned in detail.

---

## How Each Stage Runs

| Step | Who | What |
|---|---|---|
| 1. Build | Claude | The stage's features, with unit tests and a check on the local dev cluster (`make dev-up`) |
| 2. Release | Claude | Merge to `main`, tag, and release it (`gh workflow run release.yml -f tag=vX.Y.Z`) |
| 3. Image | You | Build the Valkvork golden image with `valkvork_version=X.Y.Z` (goldenimage `docs/deployment.md`, step 1) |
| 4. Cell | You | Apply `environments/aws-us-west-1-valkvork`, or replace its instances with the new image |
| 5. Workload | Together | `valkvork plan`, then `valkvork apply` the stage's manifest |
| 6. Verify | Together | Every check in the stage's table; results recorded in this file |

A stage is done when every check passes on AWS. The next stage starts after that.

Steps 3 and 4 take about half an hour per change. Stage 0 adds a faster path for fixes
found during verification.

## Stage 0: The Test Bed

No Valkvork features. Infrastructure and tooling that Stages 1 and 2 need.

| # | Change | Where | Why |
|---|---|---|---|
| 0.1 | Node groups with their own `node_class` and `host_volumes`: the controller node and the agent nodes set separately | goldenimage `environments/template-valkvork` | Today every node gets the same class and host volumes. Postgres's `pgdata` volume must be declared on exactly one node, or after a failure it can start elsewhere with an empty directory |
| 0.2 | Let nodes read workload secrets: a `workload_ssm_prefixes` input added to the nodes' IAM, e.g. `/valkv/<cell>/workloads/` | goldenimage template | Node roles can read only Valkvork's own parameters today. Stage 1's agent resolves secrets with the instance role |
| 0.3 | Workload secrets generated by Terraform (`workload_secrets`): `POSTGRES_PASSWORD`, `APG_SECRET_KEY`, `APG_ADMIN_TOKEN`, `APG_NODE_TOKEN`, as SSM SecureStrings under that prefix | goldenimage template | The manifests reference them |
| 0.4 | A dev-cell upgrade script: copy unreleased binaries to the nodes over SSM and restart the agent and controller | valkvork `scripts/` | Lets a fix be tried in minutes, without an image build. Releases still go through the image |

**Status:**
- 0.1 and 0.2 are built: goldenimage#11, which also sets `aws-us-west-1-valkvork` to the layout below.
- 0.4 is built: valkvork#8 (`scripts/dev-cell-upgrade.sh`).
- 0.3 is built: goldenimage#12. AWS generates the secrets during apply, and they are kept out of Terraform state. `tofu output workload_secret_parameters` lists the parameters.

**Cell layout for Stages 1 and 2** (`aws-us-west-1-valkvork`, two nodes). The controller node's class is `controller` since goldenimage#13 (it was `app` for the Stage 1 run). `global-pg.toml` requires it; Stage 2's `valkv-apg.toml` requires `app`, so it runs on the agent node:

| Node | Class | Host volumes |
|---|---|---|
| Controller node (controller + agent) | `controller` | `pgdata=/data/postgresql` |
| Agent node | `app` | none |

**Verify** (checked 2026-11-08 on `aws-us-west-1-valkvork`):
- [x] `valkvork node list` shows both nodes as class `app` (before goldenimage#13; after it, the controller node is `controller`).
- [x] `valkvork -o json node list` lists `pgdata` in `host_volumes` on the controller node only.
- [x] From the agent node, `aws ssm get-parameter --with-decryption --name /valkv/<cell>/workloads/POSTGRES_PASSWORD` works.
- [ ] **Fails:** the same call for `/valkv/<cell>/valkvork/controller/key` is **allowed**. The template's own policy is narrow, but the AWS managed policy `AmazonSSMManagedInstanceCore` (attached for Session Manager) grants `ssm:GetParameter` on `*`. So every node, and every container using its role, can read every parameter in the account: the controller's TLS key and admin token, and other cells' secrets. Fixed in goldenimage#14 (an explicit `Deny`); passes once that is applied. See [Findings](#findings-from-the-aws-run-2026-11-08).

## Stage 1: Postgres (`global-pg.toml`)

### Features

| # | Feature | Manifest | Notes |
|---|---|---|---|
| 1.1 | **Secret references.** Resolved by the agent with the instance role when it starts the container, and passed as environment variables. | `[secrets]`<br>`POSTGRES_PASSWORD = "ssm:/valkv/<cell>/workloads/POSTGRES_PASSWORD"` | Design in [phase-2.md](phase-2.md#secret-references). See below |
| 1.2 | **Bind address per port.** | `host_ip = "advertise"` (the node's private address), or an IP such as `"127.0.0.1"` | Default stays `0.0.0.0`, for compatibility. These instances have public IPs |
| 1.3 | **Health checks:** `tcp` and `http`. | `[check]` | Design in [phase-2.md](phase-2.md#application-health-checks). Health shows in `status`, the API, the UI and metrics. Rollouts wait for healthy. Repeated failures restart the container |
| 1.4 | **`command` and `entrypoint`.** | `[service]`<br>`command = ["postgres", "-c", "wal_level=logical"]` | As in Compose: `command` replaces the image's `CMD` and keeps its entrypoint. Stage 2's init job needs it |

**What 1.1 must do:**
- The controller stores, returns and shows only references, never values. The API, `valkvork status`, the UI, events, the database and logs all carry the reference.
- Two schemes: `ssm:` (SSM Parameter Store, decrypted) and `file:` (a path on the node, for the local dev cluster and tests).
- An unresolvable reference fails the start with a clear event naming the reference, not the value. The restart policy applies.
- A changed reference is a replacing change. A changed value in SSM is picked up at the next container start.
- Values are never written to disk by Valkvork. They are passed to Docker only, so `docker inspect` on the node shows them. That's acceptable for now, because only root can run it.

**Manifest changes:** `global-pg.toml` uses all four features.

**Status (2026-11-07): built.** On branch `feat/stage1-global-pg`; documented in [manifests.md](components/manifests.md) and [supervisor.md](components/supervisor.md):
- **Unit and behaviour tests:** 109, all passing. They cover parsing and validation, hash stability, the resolver, the agent's start path, the probes and rollout gating.
- **`make e2e`:** passes against real Docker ([local-development.md](local-development.md#tests-and-ci)). It runs Postgres with a `file:` secret, `host_ip = "advertise"`, a `command` and a `tcp` check. Then it checks the password, the bind address, an unresolvable secret, a stop-first update, adoption after an agent restart, the health metric, and a failing `http` check.
- **Not tested yet:** `ssm:` references (the AWS CLI, the node role, the region from instance metadata). They need AWS.

**Getting it onto the cell:** release it and build an image (steps 2–3), or for a first try, put this branch's binaries on the running cell with `scripts/dev-cell-upgrade.sh --cell aws-us-west-1-valkvork --bucket <bucket> --region us-west-1 --version X.Y.Z`.

**On AWS (2026-11-08):** released in v0.2.6. Verified on `aws-us-west-1-valkvork` with the dev build `0.2.99` (v0.2.6 plus the paused-container fix below), put on the cell with `dev-cell-upgrade.sh`.

### Verify on AWS

All checked 2026-11-08, except where marked.

**Placement and secrets**
- [x] `global-pg` runs on the controller node, the only one with `pgdata` (the deployed workload's node; `plan` on an unchanged manifest reports only "unchanged").
- [x] Postgres starts with the password from SSM. `psql` from the agent node, with that password, connects; a wrong password is refused.
- [x] The password appears nowhere in `valkvork status global-pg`, the UI's API (`/ui/api/overview`, `services`, `services/global-pg`, `nodes`), `valkvork events`, the agent and controller journals, or under `/data/valkvork/db/` (`grep -a`, database and WAL). The reference appears in `status`, the UI and the database.
- [x] A wrong SSM path fails the start: `FAILED: SECRET_UNRESOLVED: TEST_SECRET (ssm:/…/DOES_NOT_EXIST): aws: [ERROR]: … (ParameterNotFound)`. No container is created. Correcting the manifest runs it. (Tested with a throwaway service, so Postgres stayed up.)

**Network**
- [x] `ss -ltn` shows 5432 on `10.12.0.240` only. It is not reachable on the public IP. But on AWS the security group (5432 from `10.12.0.0/16` only) is what blocks it: AWS translates the public IP to the private address, so a private bind alone would not.

**Health**
- [x] `status` shows the workload healthy.
- [ ] **Can't pass with a `tcp` check.** With Postgres paused, its `tcp` check kept passing (for 9 minutes, until unpaused): the kernel completes the TCP handshake for a listening socket even while the process is frozen, through the published port and on the container's own IP. A `tcp` check detects a process that exits or stops listening, not one that hangs. Postgres needs an `exec` check (`pg_isready`, as compose uses): a new check type, see Findings.
- [x] The unhealthy path itself, with an `http` check on a throwaway nginx service: after `docker pause`, it was `UNHEALTHY` in 7s (3 failures, 2s apart), with an event; the agent stopped the paused container and restarted it in place; `HEALTHY` again 4s later.
- [x] Found and fixed: the agent took Docker's `paused` state for an exit and restarted the container in place. That start fails on a paused container, so the first pause test ended `FAILED: START_FAILED` and the controller replaced the workload. Fixed on branch `feat/dev-cell-upgrade-version`; the test above ran with the fix.

**Data survives**
- [x] A table created before each of these is still there after:
  - two `valkvork apply`s with a replacing change (a changed `command`, then back): the old container was gone before the new one started, both times;
  - `systemctl restart valkvork-agent`: the same container, same start time (adopted), healthy again in 5s. The `dev-cell-upgrade.sh` restart of both agents and the controller adopted it too;
  - a reboot of the controller node: Postgres was healthy again 2 minutes after the reboot, with no manual steps.
- [x] `SHOW wal_level` returns `logical`.

### Findings from the AWS run (2026-11-08)

| # | Finding | Where | Blocks |
|---|---|---|---|
| F1 | **Every node can read every SSM parameter.** `AmazonSSMManagedInstanceCore` grants `ssm:GetParameter(s)` on `*`, which overrides the template's narrow per-node policy. Fix: an explicit `Deny` on the agent role for `/valkv/<cell>/valkvork/controller/*`, and on every role for other cells' `/valkv/*` paths; or replace the managed policy with one without the parameter actions | goldenimage template | **Fixed in goldenimage#14:** `iam.tf` denies parameter reads outside each node's list. Checked with the IAM policy simulator; needs `tofu apply` |
| F2 | **A `tcp` check can't detect a hung process.** Postgres needs an `exec` check (`type = "exec"`, `command = ["pg_isready", "-U", "valkv"]`, run with `docker exec`) | Valkvork | Stage 1's pause check. Not Stage 2 |
| F3 | **A container can't reach its own node's address.** UFW's input policy is `DROP`, and a container connecting to the node's own IP (`10.12.0.240:5432`) goes through the host's input chain, where it is dropped. From another node it works (Docker's forward rules) | goldenimage image | **Fixed in goldenimage#14:** Docker's userland proxy off, so Docker NATs that traffic through FORWARD and UFW is never involved. Tested on the agent node; needs an image rebuild, or the `daemon.json` change on running nodes. Affected any container that reaches a service on its own node by the node's address. **Not Stage 2** any more: with the controller node's class `controller`, valkv-apg runs on the agent node and reaches Postgres from there, which works |
| F4 | A failed in-place restart fails the workload at once, instead of retrying under the restart policy. The controller then replaces it, which works, but the restart count and reason are lost | Valkvork | Nothing |

## Stage 2: The Gateway Control Plane (`valkv-apg.toml`)

### Features

| # | Feature | Manifest | Notes |
|---|---|---|---|
| 2.1 | **Secrets inside a value**, for URLs that embed a password. | `[env]`<br>`APG_DATABASE_URL = "postgresql://valkv:${secret:POSTGRES_PASSWORD}@postgres.<zone>:5432/valkv_apg"` | Builds on 1.1. Resolved by the agent. Any value that uses a secret is treated as secret, and shown with the secret masked |
| 2.2 | **Batch jobs**: run to completion. | `[service]`<br>`type = "batch"` | Design in [phase-2.md](phase-2.md#batch-and-system-jobs). Exit 0 is `COMPLETED` with no restart; failures retry under the restart policy. A rule for keeping finished runs. Needed for `global-pg-init`, which creates `valkv_apg` and the other databases idempotently |
| 2.3 | **An address for Postgres.** | `postgres.<zone>` in the URL | **Infrastructure, not Valkvork**, for now: the goldenimage template adds a private DNS record for the node that declares `pgdata`. Service discovery in Valkvork comes later |
| 2.4 | **Loopback-only admin port**, from 1.2. | `host_ip = "127.0.0.1"` on port 9000 | Nothing new to build; this stage verifies it |

**New manifest:** `global-pg-init.toml`. A batch job using the postgres image and
`command`, which creates the databases (`valkv_apg`, `valkv_ingress`, `valkv_krocks`,
`valkv_cloudlaunch`, `valkv_supavisor`) and the `supavisor` role. It replaces compose's
three `*-db-init` services.

### Verify on AWS

**Init job**
- [ ] `global-pg-init` runs once and shows `COMPLETED`; the databases exist.
- [ ] Re-applying it runs again and still completes (it's idempotent).
- [ ] If Postgres is down, the job retries under its restart policy, then completes once Postgres is up.

**apg-admin**

- [ ] Port 9001 is reachable from the VPC. Port 9000 is not, and listens on `127.0.0.1` only.

## Decisions (2026-11-07)

**1. Containers can use the node's role: accepted for Stages 1 and 2.**
- The golden image allows containers to reach the instance metadata service (hop limit 2), and some platform services need the role, such as global-cp launching EC2 instances.
- So any container on a node can read whatever that node's role can, including every workload secret under the prefix.
- On the controller node, that includes the controller's TLS key and admin token.
- Mitigation: run only trusted platform services on the controller node. Per-workload credentials come later.

**2. Secrets as environment variables, for now.** Files are the more secure delivery:
- A variable is visible in `docker inspect`, in the process's `/proc/<pid>/environ`, and to child processes, and it can end up in crash reports and debug output.
- A file on an in-memory filesystem, readable only by the container's user, avoids all of that and can be rotated without a restart.
- Variables come first because every service here reads its secrets from them, while only some images read secrets from files (Postgres can, with `POSTGRES_PASSWORD_FILE`).
- File delivery is a planned follow-up (NEXT_STEPS.md, "Re-evaluate").

**3. No cache of resolved secrets.**
- A container restart while SSM is unreachable fails, and the restart policy retries it.
- Revisit if it shows up in testing.

**4. Bind address: `0.0.0.0` stays the default.**
- Ports opt in per port with `host_ip`, so existing manifests behave the same.
- Re-evaluate after Stage 2: making `advertise` the default (NEXT_STEPS.md, "Re-evaluate").
